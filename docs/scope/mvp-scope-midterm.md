# windBlick — Midterm MVP scope and acceptance criteria

## 1. MVP objective

By the Midterm, windBlick demonstrates a complete desktop-browser workflow that visualizes wind turbines selected from the NRW Renewable Energies WFS in an uploaded photograph, using their recorded locations and dimensions together with explicitly supplied camera parameters.

The prototype demonstrates approximate scale and geometric placement. Reproducible example cases support the demonstration and tests; the application must also demonstrate retrieval and map selection of actual WFS turbine records. It does not promise reliable results for arbitrary photographs with unknown camera parameters, photorealism, or verified real-world visibility.

**Minimum demonstration:** Upload a photo → supply camera parameters → select a WFS turbine on the map → inspect its hub height, rotor diameter, and approval/operational status → generate the image through the Python backend → compare the original and result.

Supporting one turbine is the proposed minimum acceptance case, not a permanent restriction. User-facing descriptions remain neutral about wind power and explain uncertainty.

The same infrastructure serves two purposes:

- **Planned-turbine visualization:** Show the approximate visual presence of planned or applied-for turbines, including approved but not yet built turbines where the source explicitly identifies them. This supports residents' understanding and informed, neutral public discussion.
- **Existing-turbine comparison:** Render a selected, identifiable existing turbine from the same viewpoint as a real photograph and compare projected position and dimensions with the visible turbine. This provides an initial accuracy assessment; a single example does not establish general precision.

The selected data source is the [NRW Renewable Energies WFS](https://www.wfs.nrw.de/umwelt/erneuerbare_energien_wfs). Its [official catalogue entry](https://data.gov.de/suche/daten/standorte-der-erneuerbaren-energien-und-stromerzeugenden-anlagen-nrwc5fb7) lists operational and planning states. Preserve the source status and validate how approval status is represented in the selected feature types/attributes. In particular, do not infer approval from a generic planned status or equate approval with construction or operation. Record unknown values explicitly. Exact field names, code mappings, and record completeness must be checked against the service during implementation.

## 3. Functional acceptance criteria

These criteria are proposed for acceptance of the Midterm prototype. Record test evidence against each item; a plausible-looking image alone is insufficient.

- [ ] **AC-01 — Reproducible setup.** A team member can start frontend and backend using the documented setup commands, and the backend health check succeeds. Shared demo fixtures cover one planned/applied-for or explicitly approved-but-not-built turbine and one existing turbine identifiable in a real photo. Each case records the photo and camera parameters, WFS feature identity, coordinates, dimensions, source status, retrieval date, required elevations, units, and assumptions. One selected turbine per run is sufficient. ([#9](https://github.com/windBlick/windBlick/issues/9), [#10](https://github.com/windBlick/windBlick/issues/10), [#12](https://github.com/windBlick/windBlick/issues/12))

- [ ] **AC-02 — Photo handling.** A supported photo appears correctly oriented in the preview. The backend interprets its dimensions and orientation consistently with the frontend. An unsupported or unreadable file produces an understandable error instead of a result image. ([#20](https://github.com/windBlick/windBlick/issues/20), [#27](https://github.com/windBlick/windBlick/issues/27))

- [ ] **AC-03 — Manual camera parameters.** The demo can be completed with camera/GPS/orientation permissions unavailable. The user can supply the location, orientation, field of view, and any other parameters required by the agreed model. The interface explains units and conventions; missing required values are identified rather than silently invented. The exact field set belongs to the API contract. ([#7](https://github.com/windBlick/windBlick/issues/7), [#13](https://github.com/windBlick/windBlick/issues/13), [#28](https://github.com/windBlick/windBlick/issues/28))

- [ ] **AC-04 — WFS-based turbine selection.** The application retrieves wind-turbine records from NRW WFS for the demonstration area and displays them at their recorded locations. Selecting a turbine loads its identity, coordinates, hub height, rotor diameter, and source approval/operational status. The details and map legend explain the available status categories; unknown status remains unknown. Selecting a different turbine updates the attributes and rendering input consistently. Users do not freely place turbines or have to enter their dimensions. Missing/invalid dimensions or coordinates are flagged and prevent rendering that record; they are not silently guessed. Service retrieval and field/status mapping are demonstrated with actual records. ([#23](https://github.com/windBlick/windBlick/issues/23), [#29](https://github.com/windBlick/windBlick/issues/29), [#30](https://github.com/windBlick/windBlick/issues/30), [#39](https://github.com/windBlick/windBlick/issues/39))

- [ ] **AC-05 — Geometric correctness within the declared model.** Documented synthetic tests verify coordinate transformation, image-centre projection, orientation, scale, and elevation differences using expected values and justified numerical tolerances. A point behind the camera is excluded from normal projection and does not cause a crash. Hub height and rotor diameter retain their distinct meanings. Height assumptions are explicit; a missing height is not silently treated as zero. ([#13](https://github.com/windBlick/windBlick/issues/13), [#21](https://github.com/windBlick/windBlick/issues/21), [#22](https://github.com/windBlick/windBlick/issues/22), [#26](https://github.com/windBlick/windBlick/issues/26))

- [ ] **AC-06 — Real end-to-end rendering.** Starting with a demo photo and camera parameters, a user selects a WFS turbine through the browser. The Python backend generates the schematic turbine overlay using that record's location and dimensions, and the frontend displays the returned image with the selected turbine's identity and status. No manual API call, source-code edit, or substitution of a pre-rendered result is needed during this workflow. ([#24](https://github.com/windBlick/windBlick/issues/24), [#25](https://github.com/windBlick/windBlick/issues/25), [#31](https://github.com/windBlick/windBlick/issues/31), [#35](https://github.com/windBlick/windBlick/issues/35))

- [ ] **AC-07 — Comparison and interpretation.** Users can compare original and generated images, for example by toggling, side-by-side display, or a slider. The selected turbine's source status and data provenance remain available so that a proposed/approved project is not presented as an existing installation. Brief instructions explain the workflow and identify the result as approximate. The interface does not imply that buildings, vegetation, or terrain occlusion have been checked when they have not. ([#33](https://github.com/windBlick/windBlick/issues/33), [#34](https://github.com/windBlick/windBlick/issues/34))

- [ ] **AC-08 — Recoverable failures.** Loading is visible during service and rendering requests. Missing camera inputs, incomplete/invalid WFS records, unsupported images, empty source results, and an unavailable WFS or backend produce understandable feedback. Users can select another valid turbine or retry after availability is restored; raw internal errors are not exposed. If a saved WFS snapshot is used as a fallback, identify its retrieval date and non-live status. A snapshot does not replace evidence that WFS retrieval works. ([#20](https://github.com/windBlick/windBlick/issues/20), [#25](https://github.com/windBlick/windBlick/issues/25), [#32](https://github.com/windBlick/windBlick/issues/32), [#39](https://github.com/windBlick/windBlick/issues/39))

- [ ] **AC-09 — Contract and test evidence.** Frontend and backend use the same reviewed API v0 contract, including inputs, output format, validation errors, and an example request. The agreed automated checks run successfully in GitHub Actions, backend geometry tests pass, and the shared sample request returns a valid image. The full browser integration test and its outcome are recorded. ([#7](https://github.com/windBlick/windBlick/issues/7), [#8](https://github.com/windBlick/windBlick/issues/8), [#15](https://github.com/windBlick/windBlick/issues/15), [#26](https://github.com/windBlick/windBlick/issues/26), [#35](https://github.com/windBlick/windBlick/issues/35)) The contract also preserves selected turbine identity, source provenance, dimensions, and status, and defines how the WFS data reaches the renderer. Deterministic tests may use versioned WFS snapshots; a separate integration check records successful retrieval from the actual service.

- [ ] **AC-10 — Initial comparison with an existing turbine.** For at least one existing turbine identified by its WFS record and visible in the reference photo, compare the unadjusted model projection with the real turbine using the same image coordinate frame. Record horizontal/vertical hub-position differences in pixels and projected versus observed tower/hub height or rotor span where identifiable. Keep camera inputs, source values, photo date, and measurement uncertainty with the comparison. Rotor orientation, obscured landmarks, and uncertain base elevation are noted rather than interpreted as pure projection error. Do not manually move or resize the overlay to make this check pass. The deliverable is a reproducible initial error assessment, not a promised accuracy threshold. ([#12](https://github.com/windBlick/windBlick/issues/12), [#26](https://github.com/windBlick/windBlick/issues/26), [#33](https://github.com/windBlick/windBlick/issues/33), [#35](https://github.com/windBlick/windBlick/issues/35))

No field-accuracy threshold or performance guarantee is introduced here: the current issues do not define one. Numerical test tolerances must be stated in the test cases; they are not claims about accuracy in real photographs.

## 4. Supporting Midterm deliverables and acceptance

These are part of milestone readiness, although they are not all features of the running application.

- [ ] **S-01 — Shared implementation basis.** The scope, API contract, frontend structure, and coordinate/camera conventions are documented and reviewed by the relevant team members. Subsequent contract changes are explicit. ([#5](https://github.com/windBlick/windBlick/issues/5), [#6](https://github.com/windBlick/windBlick/issues/6), [#7](https://github.com/windBlick/windBlick/issues/7), [#8](https://github.com/windBlick/windBlick/issues/8), [#10](https://github.com/windBlick/windBlick/issues/10), [#13](https://github.com/windBlick/windBlick/issues/13))

- [ ] **S-02 — UI exploration.** Two or three Figma concepts have been compared and discussed with the frontend team. They cover the main workflow; any reference-point calibration screen is clearly marked as a future feature. ([#11](https://github.com/windBlick/windBlick/issues/11))

- [ ] **S-03 — Sensor feasibility.** A concise matrix records camera, GPS, orientation, and photo-metadata capabilities, tested device/browser combinations, unavailable values, and fallback behaviour. Untested combinations are identified. This delivers research, not a requirement to integrate live sensors into the Midterm workflow. ([#14](https://github.com/windBlick/windBlick/issues/14))

- [ ] **S-04 — WFS mapping and data checks.** Document the chosen NRW WFS feature types, feature identifiers, CRS/axis order, units, hub-height and rotor-diameter fields, and the meaning of approval/operational status values. Retain the original status alongside any display label. Check sample records in the chosen demo areas (Nottuln/Greven where suitable), record missing attributes and source limitations, and include attribution/licence information and retrieval dates. This supports mandatory source integration under AC-04; selecting the data source is no longer an open research question. ([#39](https://github.com/windBlick/windBlick/issues/39))

- [ ] **S-05 — Evaluation preparation and pilot.** Target users, evaluation objectives, user stories, and recruitment approach are documented. A short questionnaire and task-based protocol address clarity, usability, and perceived turbine dimensions. One or two people test the interface or a click-through prototype, and the main difficulties and resulting follow-up actions are recorded. Identify which prototype was tested. ([#18](https://github.com/windBlick/windBlick/issues/18), [#36](https://github.com/windBlick/windBlick/issues/36), [#37](https://github.com/windBlick/windBlick/issues/37), [#38](https://github.com/windBlick/windBlick/issues/38))

- [ ] **S-06 — Presentation and demo.** The Midterm material explains the problem, implemented workflow, demo result, initial feedback, known limitations, and next steps. A repeatable demo sequence is prepared. A clearly labelled recording or screenshots may provide presentation backup, but do not replace acceptance of the working prototype. ([#18](https://github.com/windBlick/windBlick/issues/18))

## 5. Explicitly outside the Midterm implementation scope

- **Reference-point calibration and automatic pose estimation.** These remain project goals, but [#11](https://github.com/windBlick/windBlick/issues/11) places calibration later; [#7](https://github.com/windBlick/windBlick/issues/7) only reserves room for future reference points in the API design.
- **Reliable automatic camera parameter extraction, live smartphone capture, and sensor-based orientation as mandatory inputs.** Midterm work includes feasibility research and a functioning manual fallback.
- **Free turbine placement, manual turbine-dimension entry, and automatic completion of missing source attributes.** The Midterm uses selection of NRW WFS records. Source integration and status presentation are included; a production-scale data warehouse, guaranteed NRW-wide completeness, and simultaneous multi-turbine rendering are not required for the minimum demo.
- **Automatic terrain/surface-model lookup and verified occlusion or line-of-sight analysis.** Known elevation differences still belong in the projection; a documented fixture does not require a live elevation service.
- **Photorealistic rendering, shadow-flicker/noise simulation, or legally authoritative impact assessment.**
- **Production hosting, user accounts, saved projects, and persistent photo storage.** A documented local setup is sufficient.
- **The full user study.** The one-to-two-person Midterm pilot is preparation for later evaluation, not a substitute for the broader study envisioned in the project guidance.

These exclusions limit this milestone only. They do not remove the longer-term goals in [AGENTS.md](https://github.com/windBlick/windBlick/blob/main/AGENTS.md).

## 6. Midterm acceptance walkthrough

1. Start the documented local setup and verify the backend health check.
2. Upload the shared photo and confirm orientation and preview.
3. Enter the documented camera parameters, load NRW WFS turbines on the map, and select a planned/applied-for or explicitly approved-but-not-built turbine. Confirm its source dimensions and status in the interface.
4. Generate and display the backend-rendered image; compare it with the original.
5. Switch to the existing-turbine reference case, select the corresponding WFS record, and regenerate. Compare the projection with the actual turbine in the photograph and record the initial deviations.
6. Demonstrate a recoverable input error and show the recorded results for the other failure and geometry tests.
7. Present both use cases, the WFS retrieval/mapping evidence, automated/integration checks, initial accuracy comparison, pilot feedback, and limitations.

**Acceptance rule:** The proposed Midterm MVP is ready when AC-01–AC-10 and S-01–S-06 have recorded evidence and team review. If an item is reduced or postponed, document the agreed scope change; a mockup, research result, or backup image must not be presented as an implemented feature. Parent issues [#16](https://github.com/windBlick/windBlick/issues/16) and [#17](https://github.com/windBlick/windBlick/issues/17) summarize the backend/frontend work rather than adding separate implementations.

**Before implementation:** Finalize the API and coordinate/camera conventions in their existing issues. Reconcile the FastAPI direction in [#9](https://github.com/windBlick/windBlick/issues/9) with the still-open framework wording in AGENTS.md. The product acceptance criteria do not depend on choosing Open Pioneer Trails or another frontend framework. Align issues #29 (map selection), #30 (source-derived dimensions and status instead of a manual input form), and #39 (WFS mapping and validation) with this scope clarification, and add the existing-turbine comparison to the relevant test/integration tasks. These are documentation follow-ups; the linked GitHub issues have not been edited by this document.
